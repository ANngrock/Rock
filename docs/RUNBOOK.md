# RUNBOOK — эксплуатация aegis (шаг 1)

Всё, что нужно, чтобы поднять, проверить и починить личную установку. Формула дежурства:
`make up` → `make migrate` → `make doctor` → бэкап по таймеру. Остальное — из этого файла.

## 1. Что где лежит

| Путь | Назначение |
|---|---|
| `deploy/docker-compose.yml` | postgres (pgvector), redis, searxng, nats, temporal, bot |
| `deploy/backup.sh` | `backup` / `verify` / `restore` / `list` |
| `deploy/systemd/aegis-backup.{service,timer}` | ежедневный бэкап + контрольное восстановление |
| `migrations/versions/0001_foundation.py` | вся схема шага 1 (schemas `platform/governance/memory/knowledge`) |
| `.env` | секреты и адресная часть конфигурации (не в гите) |

## 2. Первый запуск

```bash
cp .env.example .env
$EDITOR .env            # TELEGRAM_BOT_TOKEN, TELEGRAM_OWNER_ID, GLM_API_KEY — обязательны
make up                 # собирает образ и поднимает контейнеры
make migrate            # alembic upgrade head внутри контейнера бота
make doctor             # самодиагностика: конфиг + связности
docker compose -f deploy/docker-compose.yml logs -f bot
```

Проверка в Telegram (владелец, не вайтлист — молчание):

```
/status          модели, бюджет за день, версия промпта, состояние kill switch
запомни: рост 182   →  факт в memory.facts
найди в интернете курс EUR  →  web_search (SearXNG) → саммари
скинуть фото       →  analyze_image (vision-модель)
```

## 3. Конфигурация

Ключи (префикс `AEGIS_` не используется, имена — верхний регистр от полей `Settings`):

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `ENV` | `dev` | `prod` включает строгую проверку конфига (`require_runtime`) |
| `TELEGRAM_BOT_TOKEN` | — | токен от @BotFather |
| `TELEGRAM_OWNER_ID` | — | единственный пользователь, которому бот отвечает |
| `TELEGRAM_ALERTS_CHAT_ID` | пусто | чат для алертов (сначала `/start` боту, id со знаком минус) |
| `GLM_API_KEY` | — | ключ OpenAI-совместимого сервиса. Формат выдаёт владельца: `<32 hex>.<16 символов>` — z.ai/bigmodel, `sk-or-v1-…` — OpenRouter, `sk-ai-v1-…`/`sk-ss-v1-…` — ZenMux (префикс `sk-ai-v1-` выглядит как «ключ z.ai», но это ZenMux). Формат обязан соответствовать хосту `GLM_BASE_URL`, иначе 401; бот сверяет сам |
| `GLM_BASE_URL` | `https://api.z.ai/api/paas/v4/` | базовый URL **без** `/chat/completions` (хвост эндпоинта срезается автоматически, OpenAI-клиент дописывает сам) |
| `LLM_THINKING_PARAM` | `true` | `false` — не слать нестандартный параметр размышления в теле: роутеры, которые его не знают, отвечают 400 |
| `LLM_THINKING_STYLE` | `auto` | форма параметра: `auto` — по хосту (`reasoning.enabled` у OpenRouter, `thinking.type` у z.ai); `zai`/`openrouter` — вручную |
| `LLM_REASONING_EFFORT` | пусто | глубина рассуждения brain-роли, если провайдер её принимает: `low`/`medium`/`high`/`max` (GLM 5.x). Пусто = параметр не отправляется |
| `MODEL_BRAIN` / `MODEL_VISION` / `MODEL_FAST` / `MODEL_EMBED` | каталог | имена моделей; цена **и возможности** берутся по имени (`PRICES`, `THINKING_ALWAYS_ON`). В `MODEL_VISION` обязана быть модель из V-серии: `glm-4.7-flash` картинки не видит |
| `EMBED_BASE_URL` / `EMBED_API_KEY` | пусто = основной провайдер | куда ходить за векторами: чат-роутеры часто эмбеддинги не проксируют |
| `FALLBACK_MODEL` | пусто | резервная модель при 5xx/лимите; ключ и URL по умолчанию основные, дублировать секрет не нужно |
| `FALLBACK_API_KEY` / `FALLBACK_BASE_URL` | пусто | если резерв — другой провайдер, здесь его ключ и адрес |
| `KV_BACKEND` | `redis` | `memory` — запуск вообще без Redis: демо/CI/первое «пощупать». Состояние живёт только в процессе, в `ENV=prod` запрещено |
| `DATABASE_URL` | `postgresql+asyncpg://aegis:aegis@postgres:5432/aegis` | хост = `postgres` (имя сервиса) вне контейнера заменить на `localhost` |
| `REDIS_URL` | `redis://redis:6379/0` | история, pending_actions, счётчик бюджета |
| `SEARXNG_URL` | `http://searxng:8080` | self-hosted поиск |
| `SEARCH_ENGINES` | `searxng,zai` | порядок движков поиска; `zai` — `web_search` того же z.ai, что и \
модели. Пусто = поиска нет, и бот говорит об этом прямо, а не «уточните запрос» |
| `SEARCH_COST_USD_PER_CALL` | `0` | цена вызова поиска, если провайдер её выставляет: с числом расход \
уходит в `DAILY_BUDGET_USD`, иначе бюджет видит только токены модели |
| `RATE_SOURCES` | `privatbank,nbu,erapi` | источники курсов (все без ключей). Пусто = \
детерминированный путь выключен, и курс ищется через модель |
| `RATE_HOME_CURRENCY` | `UAH` | к какой валюте котируют банки в вашем регионе (не путать с \
`BASE_CURRENCY` учёта) |
| `RATE_TOLERANCE_PCT` | `1.5` | расхождение источников в допуске = «согласуются»; троекратное \
превышение = «источники спорят», и это видно в ответе |
| `DAILY_BUDGET_USD` | `2.0` | жёсткий дневной лимит: 85 % → thinking off, затем только `fast` |
| `AUTO_ALLOW_LOW_RISK` | `true` | выключить = подтверждать даже низко-рисковые записи |
| `PENDING_TTL_SECONDS` | `3600` | сколько живёт кнопка подтверждения |
| `REPRO_ENABLED` | `true` | журнал решений (M1): точные промпты, ответы, решения policy в хэш-цепочке. `false` = `/replay` и «почему ты так ответил» не работают, и бот говорит это прямо |
| `REPRO_RECORD_PAYLOAD` | `true` | писать ли содержимое запросов/ответов в `platform.blobs`. `false` экономит диск, но ход перестаёт быть воспроизводимым целиком (остаются метрики и хэши) |
| `REPRO_MAX_BLOB_BYTES` | `1048576` | потолок одного блоба: сверх — усечение с отметкой `truncated` в записи. Молча обрезать «то, что видела модель», нельзя |
| `REPRO_VERIFY_LIMIT` | `5000` | сколько записей сверять за проход `aegis repro verify` |
| `TIMEZONE` | `Europe/Moscow` | время в промпте и в `get_datetime` |
| `LOG_LEVEL` / `LOG_JSON` | `INFO` / `true` | логи идут в stderr (stdout оставлен машинному выводу CLI) |

Пустой `.env` — не поломка: `make doctor` покажет `config_missing`, а `aegis bot` откажется стартовать с внятным сообщением.

## 5. Бэкапы и восстановление (пункт 1.11)

Правило: **бэкап без `verify` не считается бэкапом**.

```bash
make backup          # pg_dump -Fc → backups/aegis_<UTC>.dump (+ .sha256, ротация, rclone)
make backup-verify   # поднимает временную БД в том же кластере, restore-ит дамп, сверяет таблицы
make backup-list     # что есть локально
make restore FILE=backups/aegis_2026-09-04T031200Z.dump   # опасная операция, перезатирает рабочую БД
```

Переменные (`deploy/backup.sh`): `AEGIS_BACKUP_DIR`, `AEGIS_BACKUP_KEEP` (14),
`AEGIS_RCLONE_REMOTE` (например `crypt:aegis-backups` — зашифрованный remote rclone),
`AEGIS_PG_SERVICE|PG_DB|PG_USER`.

Установка таймера (systemd, `Persistent=true` догоняет пропущенный ночной запуск):

```bash
sudo cp deploy/systemd/aegis-backup.{service,timer} /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now aegis-backup.timer
systemctl list-timers aegis-backup.timer
journalctl -u aegis-backup.service -n 50
```

Cron-вариант (если systemd не ваш случай — тогда сам себе напоминалка о `verify`):

```cron
40 3 * * * cd /srv/aegis && ./deploy/backup.sh backup && ./deploy/backup.sh verify >> backup.log 2>&1
```

Что проверяет `verify`: что дамп читается (`pg_restore --list`), что после восстановления есть
схемы `platform/governance/memory/knowledge`, и что таблицы `events`, `llm_calls`, `tool_runs`,
`facts`, `notes` доступны и не пустые «в никуда». Любое расхождение → exit 1.

## 6. De-escalation и деградация

| Симптом | Что происходит | Что делать |
|---|---|---|
| LLM недоступен (429/5xx, все провайдеры) | ответ деградирует: «модель недоступна», команды и парсеры работают | `make logs`; проверить `GLM_API_KEY`, при необходимости включить `FALLBACK_*` |
| Модель недоступна, а спрашивают курс | ответ приходит с детерминированного пути (`web/rates.py`): число банка + сверка с НБУ, без токенов и без бюджета | ничего — путь не зависит от LLM; `aegis doctor` покажет состояние источников |
| Postgres лёг | события/аудит не пишутся, память недоступна; бот отвечает детерминированно | проверить контейнер, `make migrate` не нужен; после поднятия всё пишется дальше |
| Redis лёг | **бот продолжает отвечать**: история хода теряется, подтверждения честно отказываются («память сессий недоступна»), бюджет считается локальным счётчиком процесса | `docker compose restart redis`; AOF вернёт ключи; в `/status` виден флаг `kv_degraded` |
| Исчерпан дневной бюджет | thinking выключается, затем только `fast`; после 100 % — отказ с текстом про `/cost` | `make psql` → `SELECT * FROM platform.v_cost_daily` ; поднять `DAILY_BUDGET_USD` |
| Нужна экстренная остановка записей | `/halt` (kill switch): write-действия запрещены, чтение живёт | `/resume` — снять |
| Подтверждение не нажато вовремя | `pending_actions` протухает по TTL, действие не выполнено | повторить запрос |

Команды бота: `/start`, `/help`, `/new` (сброс контекста), `/cost`, `/status`, `/tools`, `/halt` (заморозить записи, можно с причиной: `/halt отпуск`), `/resume`.

## 8. Обновление ценников моделей

Стоимость считается по `in_usd_per_m`/`out_usd_per_m` из `platform/gateway/models.py`; цены
провайдера меняются. Раз в месяц: сверить каталог с прайсом, поправить числа, `make test` (тесты
проверяют формулы, а не конкретные цены).

Цены лежат в `PRICES`, ключ — **имя модели**, потому что одно и то же у разных шлюзов стоит
по-разному: `glm-4.6` (z.ai, $0.6/$2.2) и `z-ai/glm-4.6` (ZenMux, ступень <32k ≈ $0.35/$1.54).
Имя переопределяется через `MODEL_*` в `.env`; если для нового имени цены в `PRICES` нет, берётся
прайс роли и в лог уходит `models.unknown_price` с подсказкой — молча врать про бюджет хуже, чем
попросить дописать строчку.

`glm-5.2` в USD-прайсе самого z.ai нет (а `open.bigmodel.cn` тарифицирует в юанях), поэтому в
каталоге держится листовая цена роутера — 1.40/4.40. Сверь её в своей консоли: заниженная цена
превращает `DAILY_BUDGET_USD` в фикцию, завышенная лишь раньше включит экономию (уровень 1).

Сверять цены и id удобно у самого роутера: `GET https://zenmux.ai/api/v1/models` отдаёт
публичный список `id / input_modalities / context_length / pricings` — оттуда и взяты строки для
`z-ai/glm-5.3-flash` (текст+картинки+видео, 1M контекста, промо $0.075/$0.25 до 09.09.2026,
лист $0.15/$0.50). В каталоге держим **листовую** цену: недооценённый бюджет ломает SLO молча, а
переоценённый лишь раньше посадит thinking в режим экономии.

Отдельная ловушка 5.3-серии: `thinking.type: "disabled"` не поддерживается (только `enabled`).
Раньше деградация бюджета именно так и экономила токены — на 5.3 это стало бы 400 на каждом
сообщении. Поэтому у имён из `THINKING_ALWAYS_ON` мы никогда не просим выключить reasoning, а
экономим сменой роли на `fast`.

Две рабочие конфигурации (выбираются только `.env`, код не меняется):

```ini
# A. z.ai / bigmodel напрямую — ключ формата <32 hex>.<16 символов>, имена без префикса автора
GLM_BASE_URL=https://api.z.ai/api/paas/v4/   # или open.bigmodel.cn — другой аккаунт и другой баланс
MODEL_BRAIN=glm-5.2             # платная (лист 1.40/4.40): с ней бюджет считает деньги
MODEL_FAST=glm-4.7-flash        # free-тиер: thinking отключается, ограничитель — частота (429)
MODEL_VISION=glm-4.6v-flash     # обязательно V-серия: у 4.7-Flash и у 5.2 нет мультимодальности
MODEL_EMBED=embedding-3         # 2048 измерений — ровно под колонку vector(2048), тот же ключ
FALLBACK_MODEL=glm-4.7-flashx   # $0.07/$0.40 — резерв на 429 бесплатной модели

# B. OpenRouter — один ключ на всё, кроме векторов; id обязателен с префиксом автора
GLM_BASE_URL=https://openrouter.ai/api/v1/
MODEL_BRAIN=z-ai/glm-5.2          # текст, 1M контекста; лист $1.40/$4.40 (у хостов бывают скидки)
MODEL_FAST=z-ai/glm-4.7-flash     # $0.06/$0.40 — сюда же уходит уровень деградации 2
MODEL_VISION=z-ai/glm-4.6v        # $0.30/$0.90: у 5.2 нет мультимодальности, только V-серия
FALLBACK_MODEL=z-ai/glm-4.7-flash # спасает от 5xx/429; от 402 (нет кредитов) не спасает
EMBED_BASE_URL=https://api.z.ai/api/paas/v4/   # OpenRouter отдаёт чужие embedding-модели,
EMBED_API_KEY=<ключ z.ai>                      # а нужен z-ai/embedding-3 = 2048 под колонку

# C. через роутер ZenMux — имена с префиксом, свои цены, своя ловушка thinking
GLM_BASE_URL=https://zenmux.ai/api/v1/
MODEL_BRAIN=z-ai/glm-5.3-flash  # 5.3-серия: thinking.type=disabled отвечает 400 (THINKING_ALWAYS_ON)
MODEL_VISION=z-ai/glm-5.3-flash # нативно мультимодальный: одна модель на обе роли
MODEL_FAST=z-ai/glm-4.7-flashx
LLM_THINKING_PARAM=false        # только если роутер отвечает 400 на thinking
EMBED_BASE_URL=                 # пусто = векторы через тот же роутер; при 404 — https://api.z.ai/api/paas/v4/
EMBED_API_KEY=                  # и тогда же — ключ z.ai отдельно
```

Три вещи, на которых они отличаются, а каталог — нет:

1. **Префикс `z-ai/` обязателен у роутера** и недопустим у z.ai. Имя модели — это строка,
   которую провайдер сверяет со своим списком, поэтому `PRICES` ключуется именем целиком.
   У самого z.ai две несовместимые зоны: `api.z.ai` (международная) и
   `open.bigmodel.cn` (Китай) — аккаунт, баланс и ключи между ними не переносятся, а ответ при
   подмене всегда один: `401` с кодом `1000`.
2. **`thinking`**: у 4.7-серии его можно выключить (экономия на уровнях деградации), у 5.3-серии
   нет — там экономия только сменой роли на `fast`.
3. **Бесплатно ≠ безлимит, а роутер ≠ бесконечный кошелёк.** Free-тиер z.ai (`glm-4.7-flash`,
   `glm-4.6v-flash`) режут по частоте: по сторонним наблюдениям порядка 1 запроса/с и ~1000/день,
   это не контракт. Поэтому `FALLBACK_MODEL` с платным `glm-4.7-flashx` — часть конфигурации по
   умолчанию, а резерв включается и одним `FALLBACK_MODEL` (ключ и адрес берутся основные, §3).
   У OpenRouter ограничитель другой — **кредиты**: `402 insufficient credits` при нулевом или
   отрицательном балансе закрывает и `:free`-варианты (20 запросов/мин и несколько сотен в день),
   а на пополнение берётся комиссия ~5.5 %. `DAILY_BUDGET_USD` считает по листу прайса, а не по
   счёту: с кэшем и скидками провайдер обычно выходит дешевле.
4. **Векторы — отдельно.** У OpenRouter свои embedding-модели есть, но `embedding-3` с нужными
   нам 2048 измерениями (под колонку `vector(2048)`) среди них нет — поэтому
   `EMBED_BASE_URL`/`EMBED_API_KEY` смотрят на z.ai. Сменишь модель
   векторов — `aegis doctor --models` покажет `dims` и потребует либо `dimensions=`, либо
   миграцию колонки.

Стоимость резерва считается по имени резервной модели (`spec_for_name`), а не по цене роли:
иначе бесплатная основная модель + платный резерв давали бы $0.000000 в трассе при реальном
расходе — и `DAILY_BUDGET_USD` переставал бы что-либо ограничивать.

Проверка после любой правки — `aegis doctor --models` (по одному запросу на роль + размерность
эмбеддинга), быстрая офлайн-проверка — `aegis doctor --quick`.

## 9. Локальная разработка без Docker

```bash
uv venv .venv --python python3.12 && source .venv/bin/activate
pip install -e ".[dev]"
make fmt lint type imports
pytest -q -m "not integration"      # интеграции требуют AEGIS_TEST_DATABASE_URL
python evals/run_golden.py
```

`pytest -m integration` поднимает схему через `alembic upgrade head` на тестовой БД; без
`AEGIS_TEST_DATABASE_URL` тесты скипаются — так и задумано, чтобы юниты оставались офлайн.

Docker для интеграций не обязателен: extra `dev` тянет `pgserver` (переносной Postgres 16 с
pgvector), и `make test-live` сам поднимает кластер в `.cache/aegis-pg`, накатывает миграции и
выполняет команду. Кластер переиспользуется, повторный прогон занимает секунды:

```bash
make test-live                       # portable-Postgres + миграции + pytest -m integration
python tools/with_local_pg.py --fresh --strip-ext -- pytest -q -m integration  # с нуля
```

Флаг `--strip-ext` вырезает из миграции trigram-индексы (в переносном кластере нет
`pg_trgm`/`pgcrypto`); на боевом образе `pgvector/pgvector:pg16` они накатываются целиком.

## 10. Диагностика «бот молчит»

1. `docker compose -f deploy/docker-compose.yml ps bot` — не в `restart`-цикле?
2. `logs bot | tail -50` — `owner_only.rejected` означает, что `TELEGRAM_OWNER_ID` не совпал.
3. Polling не работает с прокси/файрволом → в логах `TelegramServerError`.
4. Токен валиден? `curl -s "https://api.telegram.org/bot$TOKEN/getMe"`.
5. «Сбой: ...» на каждое сообщение, команды при этом живы → смотри §10.1.
6. `/status` говорит «Журнал решений: ⚠️ N сбоев записи» → миграция 0002 не накатана или диск
   кончился: бот отвечает, но ходы не воспроизводятся. `alembic upgrade head` (см. §12).

### 10.1 Сбой на всех сообщениях при живых командах

Команды (`/start`, `/status`, `/cost`) не пишут в БД, а свободный текст пишет: событие в
`platform.events` и строку в `platform.llm_calls`. Значит «команды работают, текст падает» —
это почти всегда путь записи, а не модель.

```powershell
# трейс последнего сбоя (структурный лог пишется в stderr контейнера)
docker compose -f deploy/docker-compose.yml logs --tail 300 bot | Select-String "handle.failed" -Context 0,40
docker compose -f deploy/docker-compose.yml exec bot aegis doctor --quick
```

Смотреть на `checks.postgres`: `ok: false` + `hint: накай миграции` означает, что бот поднят без
`alembic upgrade head`. Лечится тем самым `make migrate`. С тех пор как `/status` показывает
`Трассировка: ⚠️ не пишется (N сбоев)`, состояние видно без логов: откры порт ≠ пишутся строки.

Тот же корень показывает и проверка схемы:

```powershell
docker compose -f deploy/docker-compose.yml exec postgres psql -U aegis -d aegis -c `
  "select count(*) from information_schema.tables where table_schema in ('platform','governance','memory','knowledge')"
```

`0` — таблицы не создавались вовсе. Тогда сначала `run --rm bot alembic upgrade head` (его вывод
и есть настоящий лог ошибки миграции — не подавляй его), и только потом перезапуск бота.

Исторически (до фиксации) в этом положении было `Сбой: TypeError`, потому что обработчик отказа
в `BestEffortEventSink` сам кидал исключение — логирует лишний ключ `event`, который structlog
резервирует под текст сообщения. Если снова видишь TypeError в `_degradation`/`sink`-коде — это
возвращение того же класса багов, регрессия закрыта в `tests/test_degradation.py`
(в том числе статическим запретом `log.*(event=...)` по всему `src`).

### 10.2 «Модели сейчас недоступны»

Сообщение теперь всегда с причиной — она вычисляется из transport-ошибки и маскируется, так что
в Telegram не попадают заголовки и ключи:

| Причина в скобках | Что делать |
| ----------------- | ---------- |
| `401 — ключ не принят именно этим адресом` | ключ и адрес должны принадлежать **одному** сервису: ключ z.ai (`<32 hex>.<16 символов>`) не работает на ZenMux/OpenRouter, а `sk-ai-v1-…` (это ZenMux pay-as-you-go, не z.ai) не работает на `api.z.ai`. Внутри z.ai тот же фокус между `api.z.ai` и `open.bigmodel.cn`. Бот сравнивает форму ключа с хостом и дописывает вывод; после правки `.env` — `up -d --force-recreate bot` |
| `404 — неверный путь` | `GLM_BASE_URL` обязан быть `https://api.z.ai/api/paas/v4/` (OpenAI-клиент сам дописывает `/chat/completions`) |
| `429` | лимит частоты: на бесплатном `glm-4.7-flash` это ожидаемо и переживает резерв `FALLBACK_MODEL` (платный `glm-4.7-flashx`); если резерва нет — пауза или другая роль |
| `402 — не хватает кредитов` | OpenRouter: пополни openrouter.ai/settings/credits. При отрицательном балансе отказывают и `:free`-модели; `FALLBACK_MODEL` от этого не спасает — там тот же аккаунт |
| `провайдер не знает такое имя` | у роутера id с префиксом автора (`z-ai/glm-5.2`), у z.ai — без (`glm-4.7-flash`); список: `GET https://openrouter.ai/api/v1/models` |
| `Reasoning is mandatory` | хост не даёт выключать размышление: сначала `LLM_THINKING_STYLE=openrouter`, если и это 400 — `LLM_THINKING_PARAM=false`, экономия ролью `fast` |
| `соединение ... TLS` | антивирус/корпоративный прокси перехватывает сертификат; из контейнера — `docker compose exec bot python -c "import httpx;print(httpx.get('https://api.z.ai', timeout=10).status_code)"` |
| `таймаут` | поднять `LLM_TIMEOUT_S` или проверить VPN |
| `5xx` | живёт и проходит само; fallback-модель уже была перепробована |
| `провайдер не знает такую модель` | у роутеров имя с префиксом провайдера (`z-ai/glm-4.6` для ZenMux) — сверь `MODEL_*` и список роутера |
| `400` при живом ключе и верном имени | роутер не понимает нестандартный `thinking` → `LLM_THINKING_PARAM=false` |
| `Поиск не дал результатов` при живом SearXNG | это не «в интернете пусто»: SearXNG отвечает 200 и `unresponsive_engines` (обычно `google→timeout`). Бот показывает движки и статусы; обход — вторым движком `SEARCH_ENGINES=searxng,zai` |
| `поиск недоступен (searxng: НЕДОСТУПЕН ...)` | из контейнера бота адрес `http://searxng:8080`, а не `localhost`; с хоста — `http://localhost:8888` (опубликован только на 127.0.0.1) |
| `403/429` от SearXNG | `server.limiter=false` и `search.formats: [html, json]` в `deploy/searxng/settings.yml` |
| `курсы не получил — ни один источник не ответил` | проверь `RATE_SOURCES` и доступность `api.privatbank.ua` / `bank.gov.ua` / `open.er-api.com` из сети контейнера; `aegis doctor` (проба rates) скажет, кто именно |
| `401` + код `1000/1002/1003/1004` | z.ai/bigmodel: ключ неверный, просрочен или «грязный» — при копировании захватили пробел/кавычки; `1003` = перевыпустить |
| `429` + код `1113` | у z.ai/bigmodel нет средств на балансе. У владельцев Coding Plan кошелёк отдельный от подписки: проверь, что `GLM_BASE_URL` указан явно (`.../api/coding/paas/v4`) |
| `400` + код `1211` | модель с таким кодом у провайдера не существует (`1210` — это про параметры запроса, не про имя) |
| `400` + код `1261` | промпт длиннее контекста модели: уменьшить `HISTORY_LIMIT` или `FETCH_MAX_CHARS` |
| код `1302/1303/1304/1305/1308/1310/1313` | лимиты z.ai/bigmodel: параллельность, частота, дневная и недельная квоты, fair-use. Часть снимает переход brain на платную модель |
| код `1311` | текущий тариф/план не даёт доступа к этой модели — сними её в `MODEL_*` |

Одна команда проверяет всё, что связано с «бот не думает»:

```powershell
docker compose -f deploy\docker-compose.yml exec bot aegis doctor
```

В отличие от `--quick` (его использует HEALTHCHECK, чтобы не тратить бюджет и не ходить в сеть)
полный `doctor` делает настоящий запрос к модели на 8 токенов и печатает `model: ok · glm-4.5-flash
· 742 мс · $0.000010` или причину с подсказкой.

Если ключ и сеть в порядке, а бот всё равно «не думает» — проверь имена моделей:

```powershell
docker compose -f deploy\docker-compose.yml exec bot aegis doctor --models
```

Сравнение «ключ ↔ endpoint» живёт в `aegis.platform.gateway.diagnose.auth_hint_for`: оно
детерминированное (без сети), печатается в `doctor`/`--models` и отдельной строкой в `/status`
(`⚠️ ключ с префиксом sk-ai-v1-… выдан z.ai, а запрос уходит на zenmux.ai …`). Наружу уходит только
префикс ключа — значение никогда.

Каждая живая проба ограничена `_PROBE_TIMEOUT_S` (20 c): висящее соединение провайдера не должно
превращать `doctor` в «ничего не вывелось». Если в отчёте `TimeoutError: проба «brain» …` — это не
«модели нет», а сеть/прокси держит запрос; HEALTHCHECK при этом остаётся офлайн и не реагирует.

Текст деградации в чате — без разметки (`\n`, не `<br>`): он обязан читаться целиком и тогда,
когда Telegram не принял HTML (запасной путь `send_reply` снимает теги через `strip_tags`, а не
экранирует их — иначе владелец видел бы `<code>/status</code>` вместо инструкции).

По одному запросу на роль (`brain`/`fast`/`vision`) + эмбеддинги; там же печатается `dims`, так
что расхождение размерности `embedding-3` с колонкой `vector(2048)` видно сразу. Список моделей у
z.ai меняется (для картинок устойчиво существует `glm-4.5v`, `glm-4.6v` появился позже), так что
переопределение в `.env` — `MODEL_BRAIN` / `MODEL_FAST` / `MODEL_VISION` / `MODEL_EMBED` — штатный
способ удержать конфиг рабочим без правки кода.

### 10.3 Неизвестная команда

`/restart`, `/update`, `/logs` бот не выполняет — и, чтобы не списывать токены на «понимание»
таких сообщений, отвечает сразу: список команд + где перезапускают контейнер. Проверка
по форме первой косой черты, поэтому `/home/user/что-то` в текст не вмешивается.
## 11. Поиск и курсы: что работает без модели

Внешний мир в aegis разделён на два пути, и это не архитектура ради архитектуры.

**Курсы — детерминированный путь.** `src/aegis/web/rates.py` отвечает на «сколько стоит доллар/евро»
сам, до обращения к LLM: разбирает вопрос, тянет числа из публичных источников (ПриватБанк — отдельно
безналичный и кассовый, НБУ — официальный, open.er-api — агрегатор) и сверяет их между собой. Что из
этого следует:

- работает при пустом дневном бюджете, при 429/5xx провайдера моделей и при выключенном поиске;
- ответ всегда с источником и временем: чьё число, когда снято, чем подтверждено;
- одно число = «один источник, не сверено» (бот пишет именно так, а не выдаёт догадку за факт);
- расхождение в пределах `RATE_TOLERANCE_PCT` — норма маржи, троекратное превышение — «источники
  спорят», и это видно в ответе, а не сглажено;
- кросс-курс (например EUR/USD) считается делением котировок к гривне — и в ответе это сказано;
- кэш ответа живёт `RATE_CACHE_TTL_S` в KV: повтор вопроса не дёргает банк, а отказ Redis не
  обнуляет ответ.

Распознавание — отдельная функция `parse_rate_question`, и она принципиально узкая. Широкая — по
формулировке: работает «сколько сейчас евро», «почём доллар», «евро к доллару», «$/€», слово «курс»
не обязательно. Узкая — по намерению: «добавь расход 12 евро за такси» и «запомни: рост 182» курсом не
считаются, финансовый ввод по-прежнему идёт через модель и policy engine. Отдельно стоит veto по
глаголам действия («добавь», «запиши», «внеси», «потратил», «переведи»…): сообщение вида «запиши:
держим курс EUR/USD 41.5» содержит слово «курс», но это запись, а не вопрос, — перехватить его
означало бы ответить котировками и молча потерять намерение. Проверить распознавание можно офлайн:
`python evals/run_golden.py`, kind `intent` (12 кейсов, включая «не перехватывать чужие сообщения»).

**Веб-поиск — два движка, один вердикт.** `WebSearch.outcome()` возвращает не список ссылок, а
`SearchOutcome`: вердикт `ok | empty | unavailable`, отчёт по каждому движку и список правок запроса.
Разница между `empty` и `unavailable` — вся суть истории: «Поиск не дал результатов, уточните запрос»
в бою означало «SearXNG живёт в другой сети, и запрос к нему падает на connection refused». Теперь:

- `empty` — движки ответили, совпадений нет;
- `unavailable` — ни один движок не ответил, и причина по каждому уходит в текст ответа;
- `unresponsive_engines` SearXNG («google→timeout») показывается как часть диагноза, а не глотается;
- запрос сначала правится детерминированно (убрать «скажи/пожалуйста», добавить ISO-коды валют,
  суточное окно для «сегодня/курс»), при пустом ответе — одна повторная попытка исходной
  формулировкой без окна; больше ни-ни: без «агентских» циклов и лишней латентности;
- платный движок учитывается в бюджете: `SEARCH_COST_USD_PER_CALL` × число живых движков уходит в
  `CostGovernor`, иначе «бесплатный SearXNG + платный z.ai» выглядел бы как нулевой расход.

Отказ инструмента доходит до владельца отдельной строкой `⚠️ …` — её добавляет supervisor, а не
модель: правило 10 системного промпта требует передать причину дословно, но полагаться на вежливость
языковой модели в вопросе, где важна точность, нельзя.

**Проверка без Telegram:** `aegis doctor` (живые пробы `search` и `rates`, каждая ограничена 20 с) и
`aegis ask "курс доллара"` — второй обязан ответить детерминированно, без единого токена.

## 12. Журнал решений: объяснить, сверить, заякорить, воспроизвести

Хэши и метрики — не цель. Цель — чтобы на «почему ты тогда так ответил» отвечали строки из БД, а не
сочинение модели. Пишется: точный список сообщений (после DLP), ответ, `model`, токены, стоимость,
латентность, аргументы и результат каждого инструмента, решение policy **с причиной**, версия и хэш
каждого промпта, хэш схемы инструментов.

**В Telegram** (владельцу, не админу):

- `/status` — строка «Журнал решений: ведётся / выключен / ⚠️ N сбоев записи»;
- `/replay [id]` — повторить ход с тем же входом и получить вердикт судьи («эквивалентно, score
  0.93» или «НЕ эквивалентно: различаются суммы»). Без id — последний ход. Смысл в том, что
  инструменты не перевыполняются: записанные результаты уже в контексте, поэтому расхождение
  означает «модель/промпт изменились», а не «интернет сегодня другой». Критерий «что считать
  совпадением» — в файле промпта `repro/judge` (сейчас v1.1), он версионирован и захэширован: править
  смысл надо новым файлом `judge.v1.2.md`, а не текстом существующего, иначе прошлые вердикты
  перестанут объяснимо относиться к своим записям;
- «объясни, почему ты так ответил» — модель сама зовёт `explain_decision`; если записей нет, она
  обязана сказать «записей нет», а не придумать причину.

**Из CLI:**

```bash
aegis repro stats                    # сколько записей/блобов/байт, сколько сбоев
aegis repro verify --days 7          # пересчитать хэш-цепочку (0 = весь журнал)
aegis repro verify --days 1 --json   # для cron/графиков
aegis repro anchor                   # мерклов корень записей дня в governance.anchors
aegis repro replay 1a2b3c4d          # повторить конкретный ход (id из вывода aegis ask)
```

**Что означают диагнозы `verify`** — они принципиально разные:

| Строка | Что случилось | Что делать |
|---|---|---|
| `хэш не совпадает с содержимым — историю правили` | кто-то изменил строку журнала | смотреть, кто имел доступ к БД; свериться с якорём дня |
| `пропусков в порядковых номерах: N (кто-то удалял строки)` | удалили запись (триггер это разрешает только через `DROP`) | то же; при плановой ротации — фиксировать акт |
| `ссылок на утраченное содержимое: N` | цепочка цела, блоба нет: удалили или не дописали | воспроизведение этого хода невозможно, отчётность — возможна |
| `записей с усечённым содержимым: N` | `REPRO_MAX_BLOB_BYTES` меньше, чем весит контекст | поднять лимит или согласиться, что длинные ходы не воспроизводятся целиком |
| `смотрите цепочку с начала журнала` | окно `--days` началось не с первой записи | это не поломка: сверять `--days 0` |

**Якорь — единственный способ доказать, что журнал не переписали.** Superuser БД может пересчитать
хвост цепочки целиком и останется незамеченным ровно до тех пор, пока корень дня не сверен с тем, что
опубликовано вне базы. Поэтому якорь ставят по cron, а корень публикуют куда-то с датой (git tag,
письмо себе, любой каталог с timestamp):

Юниты — в репозитории (`deploy/systemd/aegis-repro-anchor.{service,timer}`, ежедневный запуск в
03:10, `Persistent=true` догонит пропущенное после простоя):

```bash
sudo cp deploy/systemd/aegis-repro-anchor.* /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now aegis-repro-anchor.timer
systemctl list-timers 'aegis-*'        # когда следующий прогон и чем закончился предыдущий
journalctl -u aegis-repro-anchor -n 20
```

Кому удобнее cron — тот же шаг строкой:

```cron
0 3 * * *  cd /srv/aegis && docker compose -f deploy/docker-compose.yml run --rm bot \
            aegis repro anchor >> /var/log/aegis-anchor.log 2>&1
```

`ots_proof` (OpenTimestamps) — колонка есть, код не сделан: офлайн-песочница не даёт ни сети, ни
блокчейна, а заявлять «заштамповано» без штампа — значит делать журнал неверифицируемым вдвойне.

**Диск.** Журнал содержит содержимое промптов: 30–80 КБ на ход с историей, ~1–2 МБ в день при
плотном использовании. `pg_dump` (§5) его бэкапит вместе со всем остальным; ротация содержимого
начнётся на шаге 6 вместе с «правом на забвение» — до тех пор удалять блобы можно (и `verify`
назовёт это отдельным диагнозом), строки журнала — нельзя.

**Отключить.** `REPRO_ENABLED=false` — если диск жалко. Тогда `/replay` честно ответит «журнал не
ведётся», `explain_decision` — «не выдумывай причину», а `/status` перестанет врать о
воспроизводимости. `REPRO_RECORD_PAYLOAD=false` — компромисс: метрики и хэши пишутся, содержимое нет.

## 13. Сверка ответов и карантин: почему бот предупредил, а не ответил молча

`⚠️ ответ не подтверждён источниками: в ответе есть «12345», чего нет в источниках` — это Verifier:
число или дата из ответа не найдены ни в одном внешнем результате этого хода, ни в вашем вопросе.
Строку добавляет код, а не модель: признавать свою ошибку она не обязана и не будет.

- предупреждение не отменяет ответ и не «исправляет» его — только помечает;
- `⚠️ … (судья недоступен — только сверка чисел)` — провайдер или сеть подвели в момент сверки:
  числа мы проверили, смысл — нет. Это не «всё хорошо» и не «ошибка»;
- `в источнике найдена попытка инструкции ассистенту (не выполнена)` — страница пыталась приказывать;
  разметчик выписал цитату, планировщик её не видел;
- ложное срабатывание возможно на округлении («43,2» вместо «43,18»). Округление — тоже расхождение
  с источником, поэтому молча его проглатывать не стали; если это мешает, поднимите
  `VERIFY_MIN_ANSWER_CHARS` или выключите `VERIFY_ENABLED` и скажите боту «не проверяй».

Настроить:

| Настройка | Смысл |
|---|---|
| `VERIFY_ENABLED=false` | не сверять ответы вовсе (экономия одного `fast`-вызова на ход) |
| `VERIFY_ALWAYS=true` | звать судью и на ответы без чисел: «НБУ отменил публикацию» числами не ловится |
| `QUARANTINE_ENABLED=false` | планировщик читает внешний текст сам (рамка `<untrusted>` остаётся) |
| `QUARANTINE_MIN_CHARS` / `QUARANTINE_MAX_CHARS` | когда разметка имеет смысл и сколько чужого текста уходит наружу |
| `MODEL_QUARANTINE=<имя>` | отдельная модель для карантина — например локальная, чтобы чужие страницы вообще не уезжали к вашему основному провайдеру |

Что посмотреть: `aegis repro replay <trace>` покажет и строку вердикта (запись вида `verdict`
разбирается объяснением хода); `GET`-запрос к журналу — `select kind, policy from
governance.decision_records where kind='verdict' order by seq desc limit 10;`. При уровне деградации
бюджета ≥1 сверка и карантин выключаются первыми: ответ важнее полировки (Runbook §8).

## 14. Напоминания: поставить, проверить таймер, понять отказ

Как это устроено, — `docs/ADR/0010`; здесь только операции. Главное, что надо держать в голове:
**бот и доставка живут раздельно**. Напоминание ставится в ходе диалога, а исполняет его отдельный
`aegis remind tick` по systemd-таймеру. Бот может лежать на время выкладки — напоминание придёт.
Тик может лежать — напоминание не придёт никогда, и это единственный способ «напоминания молчат».

### Владелец: слова в чат

```
напомни мне через 20 минут позвонить в банк
напомни завтра в 9:30 про оплату интернета
напомни в пятницу утром отправить отчёт
```

Ответ всегда содержит разбор: `Поставлено на 06.09 09:30 (через 18 ч 30 мин) — …` Если час пришлось
додумать, строка заканчивается предупреждением `время взято 09:00 — уточните, если не то`, и это не
вежливость, а признание: вы говорили «завтра», часы выбрали вы.

Что умеется: `через N минут/часов/дней/недель` (в том числе словами и «через полчаса»), `сегодня`,
`завтра`, `послезавтра`, день недели (`в среду`, `в пятницу в 10:00`), часть суток (`вечером`,
`утром`), `дд.мм`, `дд.мм.гггг`, `15 сентября в 12`, ISO `2026-09-12T08:30`. Всё остальное —
честный отказ «не понимаю»: время не угадывается. Отмена — `отмени напоминание про банк` или по
короткому id из списка; список — `что у меня запланировано`.

Время считается в поясе владельца (`TIMEZONE`, по умолчанию `Europe/Moscow`); «в 9» — это 9 у вас,
а не 9 UTC и не 9 в контейнере.

### Администратор: таймер

```bash
sudo cp deploy/systemd/aegis-reminders.{service,timer} /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now aegis-reminders.timer
systemctl list-timers aegis-reminders.timer      # NEXT/LEFT должны быть видны
```

Проверить без отправки (ничего не меняется в таблице — безопасно в любой момент):

```bash
docker compose -f deploy/docker-compose.yml run --rm bot aegis remind tick --dry-run
# или локальным окружением:
.venv/bin/aegis remind tick --dry-run
```

Ручной прогон «прямо сейчас» (реальная отправка; `Persistent=true` после простоя догоняет сам, вручную
это нужно только для проверки связности):

```bash
sudo systemctl start aegis-reminders.service
journalctl -u aegis-reminders.service -n 20 --no-pager
```

Строки, которые стоит видеть в логе: `reminder.tick claimed=1 sent=1`, `reminder.sent`, и — если что-то
не так — `reminder.delivery_failed` с причиной.

### Диагностика: почему не пришло

1. `aegis doctor --quick` — строка `reminders`: «нет таблицы» (миграция 0004 не накатана),
   «выключено», «в расписании N, просрочено M». То же — строкой в `/status` чата и списком в
   `aegis remind list`. Три разных диагноза:
   - **«некуда сохранять»** — нет БД или `REMINDERS_ENABLED=false`. Инструмент не обещает: он
     отказывает, и напоминание не поставлено;
   - **«N пора (ждут тика)»** — тик не запускался: `systemctl status aegis-reminders.timer`, дальше
     `docker compose ps` (контейнер `bot` нужен и для тика);
   - **«N с исчерпанными попытками»** — пять неудачных отправок, статус `failed`. Причина в
     `last_error` (`aegis remind list` показывает её хвостом строки). Чаще всего это Telegram 429 или
     недоступность сети у хоста.
2. Напоминание «пришло дважды» возможно ровно в одном окне: доставили, но не успели отметить `sent`
   (процесс убит между HTTP 200 и `UPDATE`). Это сознательный выбор — повтор вместо потери; если
   задвоения стали регулярными, смотрите, не умирает ли `aegis-reminders.service` по
   `TimeoutStartSec=180`.
3. Просроченное после простоя приходит пачкой, но не всей сразу: `REMINDERS_BATCH` (по умолчанию 20)
   ограничивает один проход, остальное растянется по следующим тикам.
4. «Сработало не в тот час» — почти всегда либо додуманный час (смотрите `note` в ответе бота), либо
   сбитый `TIMEZONE` у хоста и у приложения: `aegis doctor --quick | grep -i time`.

### Настройки

| Переменная | Что делает |
| --- | --- |
| `REMINDERS_ENABLED` | `false` = отказ в постановке. Не «забыли про просроченное», а явный отказ |
| `REMINDERS_BATCH` | строк за один тик |
| `TIMEZONE` | в каком поясе понимать «завтра в 9» |
| `TELEGRAM_BOT_TOKEN` / `TELEGRAM_OWNER_ID` | куда доставлять (для личного чата id владельца = id чата) |

### Что не работает специально

Повторов («каждый понедельник») нет; второй канал доставки (почта) не подключён; точность — интервал
таймера (до 5 минут); отложенное «поспать 10 минут» из самого сообщения не реализовано. Все четыре
пункта помечены как незакрытые в `docs/EXECUTION_LOG.md` (шаг 2) и в `docs/ADR/0010`, а не «когда-нибудь».

## 15. Живой ответ: включить, и что смотреть, когда правки встали

По умолчанию бот молчит, пока модель не ответит целиком, и отправляет один готовый текст.
`STREAM_REPLIES=true` меняет это: сообщение `…`, которым бот занят ход, начинает дописываться, и в
него же прилетает итог с разметкой. Решение включается одной переменой, потому что у него есть цена —
редактирования Telegram считает в общий лимит чата (см. `docs/ADR/0011`).

### Как включить

```bash
grep -n STREAM_REPLIES .env          # STREAM_REPLIES=false
sed -i 's/^STREAM_REPLIES=.*/STREAM_REPLIES=true/' .env
docker compose -f deploy/docker-compose.yml up -d --force-recreate bot
# режим видно в чате: /status -> «Живой ответ: …» (в doctor его нет: это про доставку, не про здоровье)
```

В `/status` строка «Живой ответ: включён, правка раз в 900 мс» — она там не для красоты: «молчит и
думает» и «молчит и правит» для владельца выглядят одинаково, а чинятся по-разному.

### Симптомы и что под ними чаще всего

| Владелец видит | Где причина | Что делать |
| --- | --- | --- |
| ответ пришёл дважды (черновик + отдельное сообщение) | так и задумано для ответа длиннее одного сообщения: `finish` отказывает, работает `send_reply` | ничего; если дублируется *короткий* ответ — это баг, смотреть `telegram.stream_edit_*` в логе |
| черновик остановился на полуслове | поток оборвался после первого куска: повтор запрещён, отдаётся накопленное | `journal` покажет «поток оборвался: ответ неполный»; в логе — `gateway.stream_interrupted`; дальше просто переспросить |
| правки идут рывками или не идут вовсе | лимит чата (429): пауза ≤2 с, стрим не ломается | увеличить `STREAM_EDIT_INTERVAL_MS` (1500–2500) — чаще всего этого хватает |
| разметка «поехала» в черновике | live-текст уходит без `parse_mode` — это не баг: неразрешённый тег = 400 на каждой второй правке | финальная правка всё чинит; если нет — смотреть `sanitize_html`-предупреждения в логе |
| ответ приходит так же долго, как раньше | стриминг не ускоряет модель, он раньше показывает | проверить, что `STREAM_REPLIES=true` дошёл до процесса (`/status`) |

### Где смотреть, что ход был стриминговым

У записи вызова в `governance.llm_calls` есть `response` со снапшотом: `streamed: true`, `chunks: N`,
`interrupted: true|false`. Смотреть так (`trace_id` — из footer'а ответа или из `/status`):

```sql
select ts, model, ok, error, response->>'streamed' as streamed, response->>'chunks' as chunks
  from governance.llm_calls where trace_id = '<trace>' order by ts;
```

Формат снапшота — `choices[0].message`, тот же, что у не-стриминговых ответов, поэтому
`aegis repro replay <trace>` не различает пути: ему важно, *что* увидел агент, а не *как* это
прилетело.

### Настройки

| Переменная | Что делает |
| --- | --- |
| `STREAM_REPLIES` | `true` = досылать текст правкой одного сообщения; `false` = один готовый ответ |
| `STREAM_EDIT_INTERVAL_MS` | пауза между правками, 200…10000 (по умолчанию 900) |
| `MODEL_TIMEOUT_S` | при стриминге это пауза *между чанками*, а не длительность ответа: длинный ответ
не обязан успевать в таймаут, но зависший поток оборвётся по нему |

### Чего в живом ответе нет специально

* подтверждений: кнопка «✅ выполнить» появляется на финальной правке, но сам вопрос подтверждения не
  стримится (`resume` отвечает обычным путём) — там нечего показывать по кускам;
* аргументов инструментов в черновике: пол-JSON-а аргументов — не информация владельцу, а
  подглядывание в техсостояние;
* `chat_json` (судья сверки, карантинный разборщик) не стримится: структурный ответ читаем целиком,
  `response_format` со стримом не сочетается;
* CLI `aegis ask` не стримит: терминалу нечего редактировать, и приёмника дельт у него нет.
