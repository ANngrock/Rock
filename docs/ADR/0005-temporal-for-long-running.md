# ADR-0005. Temporal — для всего, что живёт дольше одного запроса

- Статус: принят (в инфраструктуре с шага 1, в коде — с шага 2)
- Дата: 2026-09-04

## Контекст
Ход агента — не «один HTTP-вызов»: между «модель попросила действие» и «владелец нажал
Подтвердить» могут пройти часы. Наивная реализация (замкнуть процесс в памяти Python) ломается на
рестарте контейнера и не переживает деплой.

## Решение
- В шаге 1 поднимаются `temporalio/auto-setup` + UI (profile `durable`), но код их **не вызывает**:
  подтверждения живут в Redis (`pending:{id}`, TTL), а цикл агента — в процессе. Это осознанный
  промежуточный шаг, а не «временное решение навсегда»;
- В шаге 1 закладывается правильный контур: `Supervisor.handle` и `Supervisor.resume` уже разделены,
  у каждого хода есть `trace_id`, снимок сообщений сериализуем в JSON (никаких живых объектов),
  а каждый внешний вызов — это отдельный шаг с записью в трассу;
- В шаге 2 появляется workflow `AgentSession` с activity `llm_call` / `tool_run` и сигналом
  `confirm`: Redis остаётся транспортом для кнопок, состояние — в Temporal.

## Последствия
- (+) Напоминания, бюджеты, индексация и самопочинка получают один и тот же durable-механизм.
- (+) Retry-семантика долгих процессов не дублируется в бизнес-коде.
- (−) Ещё один тяжёлый сервис в контуре (Postgres + Temporal + NATS) на одном узле: платим
  операционкой за то, чтобы «долгие» процессы не были написаны на соплях.
- (−) Требует дисциплины детерминизма: никаких LLM/HTTP вызовов внутри workflow, только в activity.
