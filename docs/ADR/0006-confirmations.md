# ADR-0006. Подтверждения: pending_actions в Redis + inline-кнопки, решает policy engine

- Статус: принят (шаг 1)
- Дата: 2026-09-04

## Контекст
Самое опасное место агентной системы — момент, где «модель хочет» превращается в «данные
изменились». Убеждение в промпте («попроси подтверждение») не гарантия: его обходят галлюцинацией,
инъекцией из внешнего контента или сменой модели.

## Решение
Решает код, а не промпт:

1. `ToolSpec` несёт `writes` и `risk` — декларацию, видимую инфраструктуре, а не модели;
2. `PolicyEngine.decide(ActionContext(tool, risk, writes, source_trust, confidence, kill_switch))`
   возвращает `allow | confirm | deny`;
3. на `confirm` ход агента останавливается: в Redis кладётся снимок (`pending:{pid}`, TTL
   `PENDING_TTL_SECONDS`) со списком действий и списком сообщений, а Telegram получает inline-кнопки
   «Выполнить / Отмена»;
4. `Supervisor.resume(pid, approved, owner_id)` исполняет действия (или фиксирует отказ) и
   продолжает цикл. Снимок одноразовый (`GETDEL`), привязан к `owner_id` и содержит `trace_id`;
5. каждый вызов инструмента вместе с решением политики пишется в `governance.tool_runs`.

Важная деталь реализации: у **каждого** `tool_call` обязан быть свой `tool`-ответ, иначе
OpenAI-совместимый API отвергает следующий запрос. Поэтому ожидающие действия получают placeholder
(`[ожидает подтверждения владельца]`), который на `resume` заменяется реальным результатом: история
остаётся валидной, и модель видит исход, а не «тихий» пропуск.

## Последствия
- (+) Чужой текст (страница, чек, распознанное фото) не может вызвать запись:
  `source_trust != owner` ⇒ `confirm` независимо от риска.
- (+) Kill switch (`/halt`) — то же решение политики, а не флаг «молчать»: чтение и команды живут.
- (+) Пауза безопасна при рестартах: состояние не в памяти процесса.
- (−) Снимок сообщений в Redis — лишние байты на время ожидания (на практике < 10 КБ); компенсируется TTL.
- (−) Подтверждение — один клик на всю пачку действий одного хода; при росте пачек добавим пошаговость.
