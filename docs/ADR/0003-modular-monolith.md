# ADR-0003. Модульный монолит + Postgres-схемы по доменам

- Статус: принят (шаг 1)
- Дата: 2026-09-04

## Контекст
Проект личный, разработчик один, но требования — durable workflows, event sourcing, evals, DR.
Микросервисы на этом этапе означают сеть, контракты, деплои и наблюдаемость раньше времени.

## Решение
Один процесс-приложение (`src/aegis`) с жёсткими внутренними границами:

- домены: `memory`, `knowledge`, `web`, `finance`, `planning`, `proactivity`; слои `platform`,
  `governance`, `agents`, `interaction`;
- границы проверяет машина, а не ревью: контракты import-linter «domains are independent»,
  «platform does not import domains», «governance does not import agents or domains»;
- одна БД, но своя Postgres-схема на домен (`memory.*`, `knowledge.*`, `platform.*`, `governance.*`)
  — при выносе домена в сервис схему переносим как есть;
- инструменты агента — тонкие обёртки над use cases доменов: SQL, HTTP и бизнес-решения живут в
  доменах, handler только валидирует аргументы и форматирует результат.

## Последствия
- (+) Нулевые сетевые издержки внутри транзакции: событие и изменение состояния пишутся в одной БД-транзакции.
- (+) Границы видны в импортах и в именах таблиц — «расползание» ловится на CI (`make imports`).
- (−) Соблазн «быстро залезть в чужую схему» есть всегда — поэтому lint-imports входит в `make lint`.
- (−) Выделение сервиса — отдельная работа (свой entrypoint + миграции), зато это перенос, а не переписывание.
